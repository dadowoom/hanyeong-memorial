# 한영교회 운영 정비

이 문서는 한영교회 앱 하나의 실행 권한과 명시적인 배포 절차를 설명한다.
현재 프로그램 경로는 `/var/www/hanyeong-memorial/dist/index.js`, 작업 폴더는
`/var/www/hanyeong-memorial`, 서비스 포트는 `3060`이다.
코드 준비와 실제 서버 설치·검증은 별도 단계이며, 이 파일의 존재만으로 적용 완료를 뜻하지 않는다.

## 2026-09-08 권한 전환 결과

한영 앱은 전용 계정 `hanyeongapp`의 UID/GID `997`로 전환했다. 실제 프로세스의
관리자 권한 비트가 0이고, 홈 응답·DB 목록 조회·기존 사진·새 파일 생성 및 교체를 확인했다.
운영 프로그램은 커밋 `e02e0c6a0675b1eab25e965837c4c4459b3bc36e`를 유지했으며,
`dist`의 기존 파일 102개 내용이 모두 같고 다른 앱의 PID·재시작 횟수도 유지되었다.

실행 중 설정과 PM2 저장 파일·예비 저장 파일의 한영 항목에 전용 UID/GID,
`vizion: false`, `versioning: null`을 반영했다. 전체 `pm2 save`는 사용하지 않았다.
기존 `.env.pre*`는 root 전용 위치에 보존했고 관련 파일이 root 전용 `0600`인지 확인했다.
전용 재시작 도구를 root 소유로 설치하고, 아래의 한영 전용 명령을 실제로 호출해 검증했다.
호출 뒤에도 UID/GID `997`, 관리자 권한 비트 0이며, 보존 대상 환경 34개를 실제 프로세스의
`/proc` 정보로 비교해 같은 값임을 확인했다. `.env`의 바이트 내용과 `dist` 파일 102개가 같고,
다른 앱의 PID·재시작 횟수 및 PM2 주/예비 저장 파일의 바이트 내용도 호출 전과 같았다.
저장소 main의 운영 도구 반영과 운영 앱 배포는 구분한다. 이번 검증으로 운영 프로그램을
새로 빌드·배포하지 않았으며, 운영 앱 커밋은 위의 `e02e0c6`을 계속 유지한다.

## 2026-09-08 예약 백업과 외부 보관 확인

예약 백업 `20260908-051001`의 로컬 DB·업로드 압축 파일과 암호화된 외부
보관본을 내려받아 내용이 같은지 확인했다. DB는 테이블 12개·INSERT 문 10개이며,
압축을 끝까지 읽어 무결성과 마지막 정상 종료 표식을 확인했다. INSERT 문 수는
자료 행 수와 다르다. 백업 로그는 05:10:55, 외부 보관 로그는 05:35:04 KST에
완료로 기록되어 있다.

종료 표식의 오전 한 자리 시각 앞에는 공백 2개가 있으며 이는 정상 MySQL 형식이다.
한영 백업이 중간에 실패한 것으로 분류하지 않는다. 이번 확인은 보관본의 내용·압축
검증이며 DB에 가져오기 하거나 운영 사진을 덮어쓰는 복원 리허설은 수행하지 않았다.
한영 앱은 UID/GID 997와 기존 프로그램을 유지하며, 이 확인 때문에 재시작하거나
백업 설정·DB 자료를 변경하지 않았다.

## 운영 계정과 고정 재시작 도구

앱은 로그인할 수 없는 전용 시스템 계정 `hanyeongapp`으로 실행한다.
홈 디렉터리는 `/var/lib/hanyeongapp`이다. 이 계정은 웹 요청을 처리하는 용도이며,
서버 관리 접속이나 sudo 권한을 주지 않는다. PM2 관리 프로세스는 기존 root 계정을 유지한다.

서버 관리자가 검토한 원본을 아래 위치에 설치한다. 파일과 상위 디렉터리는 root가 관리하며
`hanyeongapp`에게 쓰기 권한을 주지 않는다.

| 저장소 원본 | 서버 설치 위치 | 소유자·권한 |
|---|---|---|
| `scripts/ops-pm2-restart.sh` | `/usr/local/bin/hanyeong-pm2-restart` | `root:root`, `0755` |

설치된 도구는 관리자가 다음처럼 실행한다.

```sh
/usr/local/bin/hanyeong-pm2-restart hanyeong-memorial
```

도구는 앱 이름 하나만 허용하고 환경변수를 비운 뒤 고정된 Python·Node·PM2를 사용한다.
실행 전에 root 호출인지, `hanyeongapp`의 UID/GID가 모두 0보다 크고 기본 그룹도
`hanyeongapp`인지 조회한다. 계정이 없거나 관리자 계정으로 잘못 연결되면 재시작하지 않는다.
PM2 목록은 출력하지 않고 내부에서 한영 하나의 실행 경로와 자동 반영 정보가 비어 있는지 확인한다.
활성 Git 정보가 있거나 대상이 중복되면 재시작을 멈추고 관리자의 점검을 기다린다.
실행 계정과 Git 정보 수집 중지 옵션을 매번 적용하며, 다른 앱 이름이나 추가 옵션은 받지 않는다.
운영 `.env`를 root 셸에서 실행하지 않는다. 앱이 낮아진 권한으로 기존 `.env`를 읽는다.
기존 운영 `.env`와 일치하는 `PORT=3060`, `NODE_ENV=production`,
`UPLOAD_DIR=/var/www/hanyeong-memorial/uploads`를 고정 설정에 명시한다.
로그인 비밀값과 DB 접속값은 기존 `.env`에서 유지한다.
일반 CLI 재시작으로 기존 PM2 환경에 고정 값만 합친다. 고정 값만 담은 JSON 파일로
재시작하면 기존 환경 키가 없어질 수 있으므로 사용하지 않는다.
CLI 재시작 후 중첩 `pm2_env.env`가 비어 보이는 경우에도 상위 유효 환경과 실제 프로세스
환경은 유지되는 것을 확인했다. 환경 보존은 중첩 객체 하나만 비교하지 않고 실제 `/proc`
환경과 상위 유효 값을 비교하며, 비밀값은 화면이나 로그에 출력하지 않는다.

## 한영만 Git 자동 반영에서 제외

확인한 서버의 `pm2-auto-pull` 2.0.1은 `pm2_env.versioning`이 있는 앱을 자동으로 갱신한다.
앱별 제외 목록을 읽는 기능은 없었다. `vizion: false`만 설정하면 이전에 수집한
`versioning` 정보가 남을 수 있으므로, 최초 운영 정비 때 한영의 `versioning: null`도 함께 지정한다.
2026-09-08 사전 확인에서는 한영의 `versioning`이 이미 비어 있었다.
이번 조치는 Git 정보가 다시 수집되어 자동 반영이 재활성화되는 일을 막기 위한 설정이다.
이후 전용 도구는 `versioning`이 비어 있다는 사전 검사와 `--no-vizion`으로 이 상태를 유지한다.
최초 정비에 JSON 재시작이 필요하면 현재 한영의 실제 유효 환경 전체를 확인해 복사한 뒤
고정 값을 합친다. `pm2_env.env`만으로 실제 환경 전체를 얻었다고 가정하지 않는다.
이 작업은 root 전용 파일에서 수행하고 비밀값을 출력하거나 저장소에 넣지 않는다.

공유 자동관리 모듈과 다른 앱은 그대로 운영한다. 변경 직후와 자동 확인 주기가 여러 번 지난 뒤
한영의 `vizion`이 false이고 `versioning`이 없거나 null인지 확인한다.
다른 앱의 자동 반영 관련 설정과 PID·재시작 횟수가 유지되는지도 비교한다.
이번 설정은 한영의 장애 자동 재시작 기능을 끄는 설정이 아니다.

재부팅 후에도 유지하려면 root의 PM2 저장 파일과 예비 저장 파일 각각에서 한영 항목만
숫자 UID/GID, HOME·PORT·NODE_ENV·UPLOAD_DIR와 대응하는 `env` 값,
`vizion: false`, `versioning: null`을 반영한다.
`env` 안에 UID/GID·versioning 관련 값이 있으면 상위 설정을 덮을 수 있으므로 먼저 확인한다.
원본은 root 전용 위치에 백업하고, 다른 앱 항목의 JSON 내용과 순서가 완전히 같은지 검증한다.
전체 `pm2 save`로 다른 앱의 저장 설정까지 갱신하지 않는다.

## 파일 접근과 사전 백업

현재 앱 코드에서 직접 쓰는 경로는 `UPLOAD_DIR` 아래다. 기본 운영 경로는
`/var/www/hanyeong-memorial/uploads`이며 실제 서버 `.env`의 값을 먼저 확인한다.
업로드마다 임의 접미사가 붙은 새 파일을 만들므로 기존 업로드 파일 소유자를 일괄 변경할 필요는 없다.

- `.env`는 root 소유를 유지하고 `hanyeongapp` 그룹에 읽기만 허용한다.
- 업로드 루트와 모든 하위 디렉터리에 전용 그룹의 쓰기·탐색 권한 및 그룹 상속을 부여한다.
- 앱 코드·의존성·정적 파일은 전용 계정이 읽을 수 있어야 한다. PM2 소켓과 root 홈은 열지 않는다.
- 권한 변경 전 디렉터리별 소유자·그룹·권한, 기존 `.env` 권한, PM2 대상 설정을 기록한다.
- 배포 전 기존 프로그램·의존성·업로드와 DB 백업의 복원 가능 여부를 확인한다.
  백업과 비밀 설정은 공개 저장소에 넣지 않는다.

## 명시적인 배포와 확인

GitHub 반영만으로 한영 운영 코드가 바뀌는 흐름은 사용하지 않는다.
관리자가 적용할 커밋을 정하고 다음 순서로 진행한다.

1. 로컬의 해당 커밋에서 의존성 고정 설치, 타입검사, 테스트, 빌드를 마친다.
2. 서버의 현재 커밋과 수정된 파일을 확인하고 필요한 원본을 보존한다.
   `git reset --hard`로 운영 서버의 수정 파일을 지우지 않는다.
3. 기존 운영 파일을 유지한 상태에서 배포 후보를 준비하고, 실패 시 되돌릴 프로그램·의존성을 확보한다.
4. 검토한 후보를 한영 경로에 반영한 뒤 고정 재시작 도구로 한영만 재시작한다.
5. 지정된 포트의 홈·연혁·공개 기념관·관리자 로그인 화면과 기존 업로드 파일을 확인한다.
   HTTP 200만 확인하지 말고 실제 화면과 필요한 데이터가 정상인지 함께 확인한다.
6. PM2의 앱 이름·실행 경로·상태, 실제 프로세스의 UID/GID와 관리자 권한 비트 0,
   새 시험 파일 업로드 권한, 다른 앱의 PID·재시작 횟수 보존을 확인한다.
7. 적용 커밋, 백업 위치, 검증 결과, 복구 방법을 운영 기록에 남긴다.

시작 코드에는 요청한 포트가 사용 중이면 다음 포트를 시도하는 기존 동작이 있다.
따라서 PM2의 online 표시만으로 성공 판단을 하지 않고 반드시 지정 포트 `3060`도 확인한다.
이번 정비에서 앱 화면, 로그인, DB 구조, 프로그램의 시작 코드는 변경하지 않았다.

검증 기록: 기존 애플리케이션 타입검사·7개 파일의 테스트 19개·빌드를 통과했다.
전용 도구 테스트 11개와 Bash 문법 검사도 통과했다. 도구 테스트는 서버에 접속하지 않고
계정·인자 제한, 경로와 자동 반영 정보 확인, PM2 오류·시간 초과 및 비밀값 출력 차단을 검증한다.

```sh
pnpm install --frozen-lockfile
pnpm check
pnpm test
pnpm build
bash -n scripts/ops-pm2-restart.sh
python3 -B scripts/ops-pm2-restart.test.py
git diff --check
```

이상이 생기면 현재 상태를 먼저 기록하고 한영만 복구한다. 앱 권한을 root로 되돌리는 복구는
임시 조치로 기록하고, 원인 확인 후 다시 전용 계정으로 실행한다.
공유 PM2 전체 재시작·자동관리 모듈 전체 중지·다른 앱 설정 일괄 복원은 하지 않는다.

## 2026-09-08 업로드 저장공간 전환

`/var/www/hanyeong-memorial/uploads`는 추가 디스크의
`/data/service-uploads/hanyeong-memorial/uploads`에 bind mount로 연결된다.
사진 URL과 DB는 그대로이며 원본은 관리자 전용 보관소에 보존했다.

고정 재시작 도구는 root가 관리하는
`/usr/local/lib/dadowoom-storage/upload-mount-guard.py`로 정확한 디스크 연결을
확인한다. 누락·다른 서비스 폴더 연결·읽기 전용 연결이면 재시작을 거부한다.
연결이 빠진 기본 디스크의 빈 폴더는 root 소유 0000 권한으로 쓰기를 막는다.
통합 백업에도 한영과 화순만 대상으로 같은 연결 검사를 설치했다.

새 서버의 운영 도구 설치 전에는 `work-docs/ops/upload-storage`의 검토된 guard와
한영 전용 mount unit부터 설치한다. guard는 root 소유로 앱이 수정할 수 없어야 한다.
공용 PM2 설정과 다른 앱은 변경하지 않는다. 현재 서버의 전환 도구는 재실행하지 않는다.
연결 해제 시 쓰기 차단·재연결·시험 파일 저장 및 제공·압축 포함을 검증했다.
전체 서버 재부팅은 시행하지 않았다. 복구할 때는 새 디스크에만 생긴 최신 파일을
보존해야 하며, 과거 원본으로 단순 교체해서는 안 된다.
